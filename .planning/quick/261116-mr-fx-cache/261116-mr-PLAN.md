# Quick 261116-MR — Provider-side caching for /api/convert

## Problem

`GET /api/convert` took 0.8–1.9s — no faster than calling Frankfurter
directly (0.7–1.05s) — because the route fetched the upstream per request
(per-pair endpoint, `revalidate: 3600` per pair URL), even though the rates
are a **daily fixing** that changes once per business day. Per Hector's
fix-the-API rule (2026-11-16): when a shared API is slow enough that
rebuilding inside a consumer looks faster, fix the API — and caching is the
provider's responsibility, done on the provider's side.

## Change

- New `src/lib/fxRates.ts`: fetches the full Frankfurter v2 USD-base table
  (~200 quotes) once into the Next Data Cache (`next.revalidate = 3600`,
  tag `fx-rates`) and resolves pairs in-process — USD pairs verbatim,
  inverses/crosses computed and rounded to Frankfurter's 5-significant-figure
  publishing precision so values match the per-pair endpoint.
- `rateDate` is always the payload's own per-quote fixing date (stalest leg
  for crosses) — a cached table is never relabelled as today's rates.
- Route order: cached table → per-pair endpoint → currency-api mirrors
  (fallbacks unchanged, so long-tail codes Frankfurter lacks still work).
- Success response gains `s-maxage=3600` (browser `max-age` unchanged) so
  shared caches/CDN can serve repeat conversions without reaching the
  function. Response body shape is unchanged.

## Verify

- vitest: fxRates unit tests (parse, verbatim USD pairs, 5 s.f. crosses,
  stalest-leg dating) + a route test proving the table path answers without
  touching the per-pair/fallback upstreams.
- Live after deploy: benchmark MoneyRate vs Frankfurter direct,
  USD/CAD + USD/EUR + USD/JPY, cold and warm.
