## Color

App is DaisyUI dark-by-default with a light/dark toggle — color roles below are theme-token references, not fixed hex, so both modes are covered automatically.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `bg-base-100` (`--b1`) | Overlay dimming layer over the page (driver.js `overlayColor` must resolve to this token's computed color, see below) |
| Secondary (30%) | `bg-base-200` (`--b2`) | Popover surface background |
| Accent (10%) | `bg-primary` / `text-primary` (`--p`) | **Reserved for: the "Next" button fill, the active progress dot, and the spotlight ring border around the highlighted element.** Not used for Back/Skip buttons, not used for body text. |
| Destructive | `text-error` / `btn-error` (`--er`) | Not used in Phase 1 (no destructive action exists in the tour itself — "Skip" is a neutral dismissal, not destructive, so it uses ghost/neutral styling, not error red) |

Accent reserved for: **(1)** Next/Done button background, **(2)** active step's progress-dot fill, **(3)** the spotlight cutout's focus ring (`box-shadow` ring around the highlighted `data-tour` element). Everything else (popover surface, Back button, Skip link, body text, borders) uses neutral base tokens.

**Overlay dimming:** driver.js draws its own SVG overlay; set `overlayColor` to a semi-transparent neutral (not `--b1` directly, since driver.js expects a raw color string, not a CSS var function in older versions) — use `rgba(0, 0, 0, 0.65)` for dark theme and `rgba(0, 0, 0, 0.45)` for light theme, switched at tour-init time by reading `themeAtom`. This keeps the dim neutral/black-based regardless of theme (standard spotlight-tour convention) rather than tying it to `--b1`'s actual hue, since a hue-tinted scrim reads as a visual bug.

driver.js renders its own DOM (`.driver-popover`, `.driver-overlay` SVG mask, `.driver-active-element` class on the highlighted target) outside React's tree, appended to `document.body`. Style it via a dedicated CSS file (e.g. `src/theme/tour.css`, imported once in `src/app/layout.tsx` or lazily alongside the tour init) that overrides driver.js's default classes with DaisyUI tokens — do NOT use driver.js's inline JS-based `popoverClass`/theme options for colors; use CSS overrides so the popover follows the live theme without re-initializing the tour on theme change.

| Property | Value | Rationale |
|---|---|---|
| Popover background | `oklch(var(--b2))` (`bg-base-200` equivalent) | Matches existing "elevated surface" token used by inputs/search-results (`SearchBar.tsx` uses `bg-base-200`) |
| Popover text | `oklch(var(--bc))` | Matches app-wide text color token |
| Popover border | `1px solid oklch(var(--bc) / 0.15)` | Subtle separation from page background, consistent with `.divider` opacity pattern already in `globals.css` (`oklch(var(--bc) / 0.3)` used for range-track) |
| Popover border-radius | `1rem` (`var(--rounded-box)`) | Matches DaisyUI's own `.modal-box` radius so the tour popover doesn't look like a foreign component next to `CurrencyListModal` |
| Popover max-width | 320px (mobile-safe default; Phase 3 does the full mobile audit, but Phase 1 must not overflow small viewports since steps 1-2 anchor on rows that exist on first load) | Matches driver.js default-ish sizing, keeps body copy ≤110 chars from wrapping to more than 3 lines |
| Popover padding | 16px | Per spacing scale `md` token |

## Interaction Timing & Loading States

**Hydration gate (must-not-violate):** `page.tsx` already establishes a `hydrated` boolean (`useState` flipped `true` in a `useEffect`, `page.tsx:113-114`) specifically to avoid SSR/localStorage mismatches. The tour's "seen" flag read AND the tour's auto-start decision must both wait for `hydrated === true`. Do not read the new `tourSeenAtom` value for the auto-start check before this flag flips — otherwise SSR renders "unseen" (no localStorage), then client hydration may flip to "seen," causing a flash-start-then-cancel.

**Skeleton gate (must-not-violate):** `page.tsx:262-276` renders a full skeleton (shimmer placeholders) while `isLoad1 && !effectiveAll` — none of the 8 anchor elements exist in the DOM during this state (the skeleton replaces the entire `<main>` content, including where `#currencyList` and the control row would be). The tour must NOT call `driver.start()` while the skeleton is showing, or driver.js will either throw (selector not found) or spotlight nothing.

**Concrete start condition** (AND of all three):
1. `hydrated === true`
2. Skeleton is gone — i.e., `effectiveAll` is truthy (real data OR the `getDataFromLocalStorage` stale fallback resolved)
3. `tourSeenAtom` (new atom, see State Contract below) is `false`

Implement as a `useEffect` with all three as dependencies; call `driverObj.drive()` only once the effect body confirms the condition, and guard with a `useRef` "already started" flag so React StrictMode's double-invoke in dev doesn't double-start the tour.

**Historical-date edge case:** if a returning visitor's shared link (`?base=&amount=&show=`) or session state has `historicalDate` set before the tour would start, step 7's anchor (`tour-historical-date`) still exists (the date input renders regardless of historicalDate value) — no special-casing needed, but note the tour must not fire mid-way through the shared-link hydration `useEffect` (`page.tsx:122-131`) resolving, since that effect can change `baseCur`/`currency2Display` after initial render. Sequence the tour start AFTER that effect settles — in practice this is already satisfied because that effect has an empty dependency array (runs once, synchronously ordered before the data-driven gates above resolve on first paint).

**Step 4 — modal state constraint:** step 4 spotlights the *trigger button* (`tour-list-settings`), not the modal's interior. The `<dialog id="currency_list_modal">` must remain CLOSED throughout step 4 — do not auto-open it. This avoids the native-`<dialog>` top-layer/`::backdrop` stacking fight with driver.js's overlay (native dialogs render in the browser's top layer, above ordinary z-index stacking, which would visually bury driver.js's spotlight ring under the DaisyUI modal backdrop if both were open simultaneously). If the user manually opens the modal while step 4's popover is showing, the tour's "Next" advances normally after the user closes it — no special handling required, since driver.js re-queries the next selector fresh on each step.

## Edge Cases

**Virtualized list (`react-window` `FixedSizeList`, >40 rows):** `page.tsx:238` sets `shouldVirtualize = !isEditing && rows.length > VIRTUALIZE_THRESHOLD (40)`. When virtualized, only the rows currently scrolled into the viewport exist in the DOM — a row that isn't rendered has no `data-tour` attribute present at all, which would break step 1/2 if the base currency's row happens to be scrolled out of view.

- **Default installs are safe:** `DefaultCurrency2Display` (checked in `src/lib/constants.ts`) is well under 40 currencies for a first-time visitor with no customization, so virtualization never activates during a fresh first-run tour. This is the expected Phase-1 path and needs no extra code.
- **Defensive spec regardless:** because steps 1-2 target "whichever row is currently base" (see anchor map — `data-tour` is applied conditionally on `isBase`, not on array position), the base row is guaranteed to exist in the DOM as long as it is visible/scrolled-to. If a future returning visitor with >40 currencies ever re-triggers the tour (e.g. manually via Phase 2's replay control) and their base row is scrolled out of the virtualized viewport, driver.js's selector query will fail silently for that step. **Contract: the tour must call `element.scrollIntoView({ block: 'center' })` (or rely on driver.js's built-in `scrollIntoViewOptions`) before each step transition**, and if the target selector still resolves to `null` after a short retry/timeout, **skip that step silently** (advance the step index without showing an error state — matches the "Error state: not applicable" copywriting entry above) rather than blocking tour progress.

**Small viewport / offscreen anchor:** Phase 3 owns the full mobile audit (A11Y-02), but Phase 1 must not actively break on mobile since the tour auto-starts for every first-time visitor regardless of device. Contract for Phase 1 (minimum, not exhaustive): driver.js's default `scrollIntoViewOptions: { block: 'center' }` must be enabled globally in the tour config so each anchor scrolls into view before its popover renders, and popover placement must use driver.js's `side: 'auto'`/auto-flip behavior (not a hardcoded `side: 'bottom'` for every step) so a popover for a bottom-of-screen anchor (e.g. step 8, PWA install in the footer) doesn't render off-screen.

**PWA install anchor may have no visible button:** `InstallButton.tsx:30` returns `null` entirely when `!deferred` (no captured `beforeinstallprompt` event — true for most desktop Safari/Firefox, already-installed PWAs, and browsers that never fire the event). Per the anchor map, wrap with an always-present `<div data-tour="tour-install">` so the selector never 404s, but **the spotlight will highlight an empty/zero-height container** when the button itself isn't rendered. Contract: if `deferred` is `null` when step 8 is reached, show the step 8 popover anchored to the (empty) footer container but swap the body copy to a fallback string: **"Look for an install option in your browser's menu — moneyrate works offline once installed."** (translation-ready, same rules as other body copy). Do not skip step 8 outright — TOUR-06 requires exactly 8 steps every time; silently dropping one would make the "n / 8" counter's final count for this step (e.g. "8 / 8" text) inconsistent with skipped-vs-shown step count. (This fallback-copy behavior is a Phase 1 decision recorded here because it's a visual/copy contract question, not a re-litigation of TOUR-06's step count.)

**First-time visitor whose default base currency row happens to be the very first row rendered:** no special case needed — step 1's anchor targets "the base row" by `isBase`, so it naturally works whether the base currency sorts first, last, or anywhere in the display order.

## State Contract (for planner/executor — not a new design decision, restating the locked pattern)

New atom in `src/lib/atoms.ts`, following the exact existing convention (see `isEditingAtom`/`isDefaultCurrencyValueAtom` for shape reference):

```ts
export const tourSeenAtom = atomWithStorage<boolean>('tourSeen', false);
```

- Read/write only after `hydrated === true` (see Interaction Timing).
- Set to `true` at the moment of: (a) reaching/confirming step 8's "Got it, let's go" CTA, OR (b) clicking "Skip tour" at any step, OR (c) any driver.js `onDestroyed`/`onCloseClick` callback firing for any reason (covers clicking the overlay backdrop or pressing Escape, if driver.js's default close-on-overlay-click/Escape behavior is left enabled — confirm this default in Plan 1 research and either keep it consistent with "closes immediately" TOUR-04 wording, or disable overlay-click-to-close if the planner decides accidental dismissal is a risk. This spec requires that WHICHEVER close paths are enabled, all of them set `tourSeenAtom = true`, with no path that closes the overlay while leaving `tourSeenAtom` at `false`).
