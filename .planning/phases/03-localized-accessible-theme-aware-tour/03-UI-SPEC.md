# Phase 3 — UI Design Contract

> Visual and interaction contract for making the existing Phase 1–2 tour a first-class citizen of moneyrate's i18n, accessibility, and theming systems (I18N-01, A11Y-01, A11Y-02, LANG-01-pulled-forward). Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **This spec EXTENDS `01-UI-SPEC.md` — it does not replace it.** Copy content, anchor map, spacing/typography/color tokens, and popover visual contract established in Phase 1 remain authoritative except where explicitly overridden below (responsive popover width, focus rings, reduced motion, localization, RTL).

## Typography

Unchanged from Phase 1 (`01-UI-SPEC.md` §Typography) — 2 weights (400/600), 3 sizes (12/14/16px) — reused verbatim for every localized string. **New constraint:** translated strings (D-06, 30 locales) MUST fit the same visual budget as the English source:

| Role | Size | Weight | Line Height | Localization constraint |
|------|------|--------|-------------|--------------------------|
| Popover title | 16px | 600 | 1.2 | ≤ 4 words / ≤ 40 characters in any locale (CJK/Cyrillic count as 1 char/glyph each — budget by rendered width, not byte length) |
| Popover body | 14px | 400 | 1.5 | ≤ 110 characters in Latin scripts; ≤ 55 characters (glyphs) in CJK (zh-TW, zh-CN, ja, ko) since each glyph is visually ~2× the width of a Latin character at the same font-size |
| Step counter / progress text | 12px | 400 | 1.2 | Numeral format only (`"3 / 8"`) — the `/` separator and digits are locale-invariant, no translation needed for this string itself |
| Button label (Next/Back/Done) | 14px | 600 | 1.2 | ≤ 12 characters per button label in any locale — this is the tightest budget in the contract because 3 buttons plus the progress text must fit one `.driver-popover-footer` row at the mobile popover width (see Responsive Popover Width below) |

RTL note: font metrics are unaffected by `dir="rtl"` — Arabic/Urdu glyphs at 14-16px render at roughly the same or narrower visual width than Latin at equivalent character counts, so no separate size reduction is needed for `ar`/`ur`, only directional layout changes (see RTL Contract below).

**Authoring rule (D-06):** Claude authors all 30 locales this phase, English first, then translated to match the tone/length of each locale's existing `home`/`settings` entries in `translations.ts` (e.g. casual/friendly register, occasional emoji in settings labels — the tour's `home`/`settings` sibling namespaces do NOT use emoji in body copy, so `tour` should not introduce emoji either, to keep the tour visually distinct from settings-menu chrome). Keep every translated string within the character budgets declared in Typography above. ## Locale Source & LANG-01 Contract (D-01, D-02, D-03)

**D-01/D-02 — single source of truth:** the tour's locale is `languageAtom` (read via `useTranslation()` / `translations[language]`), the exact same source the rest of the chrome uses. `startTour()` (`src/app/page.tsx:170`) currently computes `const locale = resolveTourLocale(navigator.languages, SUPPORTED_LOCALES, 'en')` — **this line must change** to read the app's active language atom instead (e.g. accept `language` as a parameter to `startTour()`, sourced from the existing `i18n` var no — from the `languageAtom` value directly, since `i18n` is already the resolved dictionary not the code). Concretely: `startTour()` should receive or close over the current `Language` code from `useAtom(languageAtom)` and pass it into `buildTourSteps(locale)`, replacing the `resolveTourLocale(navigator.languages, ...)` call at that call site entirely. `resolveTourLocale` itself is NOT deleted — it is repurposed for D-03 below.

**D-03 — first-load device default (LANG-01 pulled forward):** on first load only (no `language` key yet present in `localStorage`), default `languageAtom` to `resolveTourLocale(navigator.languages, SUPPORTED_LOCALES, 'en')`. This must run as a **client-only effect gated behind the existing `hydrated` flag** (`src/app/page.tsx:123-124`), never at module-eval time in `atoms.ts` (server always renders `'en'`; computing the device default during SSR/module-eval would cause a hydration mismatch when the client recomputes a different locale). Recommended placement: a new `useEffect` in `page.tsx`, guarded by `hydrated` and a check that no stored `language` value exists yet (e.g. `getDataFromLocalStorage('language', null) === null`), that calls `setLanguage(resolveTourLocale(navigator.languages, SUPPORTED_LOCALES, 'en'))` exactly once. A stored user choice always wins thereafter — this effect must never fire again after the first successful write. Sequencing: this effect should resolve before or in the same tick as the tour's own start-gate check, so the very first tour render already reflects the device-derived language (avoids a flash of English tour copy before the effect settles) — in practice both are gated on `hydrated`, so ordering them consecutively in the component body (language-default effect above the tour-start effect) is sufficient; no additional synchronization primitive is needed.

## Keyboard Accessibility Contract (A11Y-01, D-07)

driver.js already provides arrow-key step navigation, Esc-to-close, and a focus trap inside the popover (`allowKeyboardControl: true`, `src/app/page.tsx:197`) — **do not reimplement any of this.** This phase adds exactly three things, all additive:

### 1. `:focus-visible` outline rings

Author in `src/theme/tour.css` (same file as the existing popover theme, per the file's own header comment convention). Applies to driver.js's real button classes (confirmed in `src/theme/tour.css:44-71`: `.driver-popover-next-btn`, `.driver-popover-prev-btn`, `.driver-popover-done-btn`, `.driver-popover-close-btn`) plus the app's `<button>` for the "?" replay control at `src/app/page.tsx:387-395`.

| Property | Value | Rationale |
|---|---|---|
| Outline width | `2px` | Matches the spotlight ring width already used for `.driver-active-element` (`src/theme/tour.css:93`, `box-shadow: 0 0 0 2px oklch(var(--p))`) — visual consistency between "this is highlighted by the tour" and "this is keyboard-focused" |
| Outline offset | `2px` | Standard breathing room so the ring doesn't overlap the button's own border/background, consistent with browser default `:focus-visible` conventions |
| Outline color | `oklch(var(--p))` | Same accent token used everywhere else (see Color section) — no new hue introduced |
| Outline style | `solid`, applied via `outline: 2px solid oklch(var(--p)); outline-offset: 2px;` | Uses `outline` (not `box-shadow`) so it composes independently of the popover's own `box-shadow` (`0 10px 25px -5px rgb(0 0 0 / 0.3)`, `tour.css:18`) without needing a multi-layer `box-shadow` list |
| Selector | `:focus-visible` only, never bare `:focus` | Matches modern a11y convention — keyboard focus shows the ring, mouse/touch clicks do not (avoids a distracting ring on every tap) |

Concrete rule set to add to `tour.css`:
```css
.driver-popover-next-btn:focus-visible,
.driver-popover-prev-btn:focus-visible,
.driver-popover-done-btn:focus-visible,
.driver-popover-close-btn:focus-visible {
  outline: 2px solid oklch(var(--p));
  outline-offset: 2px;
}
```
The "?" replay button's ring is authored the same way but targets the app's own button element — since it's a regular React button (not inside driver.js's portal), it may live in `tour.css` (grouped under a comment noting it targets the replay control) or in `globals.css` next to the existing `CurrencyRow.tsx:107` focus-outline pattern. **Recommendation: keep it in `tour.css`** since it is conceptually part of the tour's a11y surface and D-07 groups both under one bullet — add a `data-tour-replay` attribute or reuse the button's existing `aria-label="Replay tour"` as the CSS hook is unnecessary; simplest is a stable class, e.g. `.tour-replay-btn:focus-visible`, added to the button's `className` in `page.tsx:387-395` alongside its existing classes.

### 2. Focus restoration

On tour close/done (any of the three existing exit paths already wired at `src/app/page.tsx:206-216` — `onDoneClick`, `onCloseClick`, `onDestroyed`), return keyboard focus to the element that triggered the tour:
- If triggered by the "?" replay button click → restore focus to that button.
- If auto-started (no user-triggered element) → restore focus to the "?" replay button as the sensible default landing point (it is the tour's permanent, always-visible entry point per Phase 2), rather than `document.body` or leaving focus wherever driver.js's teardown drops it.

Implementation contract: capture `document.activeElement` (or a ref to the "?" button, simpler and more reliable since driver.js's own focus trap may have already moved `document.activeElement` before teardown) at the moment `startTour()` is invoked, and call `.focus()` on it inside the shared exit handler. Since all three exit paths (`onDoneClick`/`onCloseClick`/`onDestroyed`) already funnel through the same `driverObj` config object, add one shared cleanup (e.g. a local `restoreFocus()` closure referenced by all three callbacks) rather than duplicating the `.focus()` call three times.

### 3. `prefers-reduced-motion`

Add a `@media (prefers-reduced-motion: reduce)` block to `tour.css` that removes driver.js's popover transition/animation. Since driver.js's animation is controlled by both a JS config flag and its own CSS (`--driver-animation-duration` is driver.js's one exposed custom property, per `tour.css:2-3`), the contract has two parts:

- **CSS:** 
  ```css
  @media (prefers-reduced-motion: reduce) {
    .driver-popover {
      --driver-animation-duration: 0ms;
    }
  }
  ```
- **JS:** read `window.matchMedia('(prefers-reduced-motion: reduce)').matches` once inside `startTour()` (same pattern as the existing one-time `isDarkTheme` read at `page.tsx:191`) and conditionally set `animate: false` and `smoothScroll: false` in the driver config object (currently `smoothScroll: true` unconditionally at `page.tsx:199`; `animate` is not currently set, meaning driver.js's own default of `true` applies — this phase makes both conditional on the media query).

This clears the reduced-motion item explicitly deferred from Phase 2's context (`02-CONTEXT.md` "Deferred Ideas": "Keyboard-focus/reduced-motion/mobile hardening of the control → Phase 3").

## Mobile / Touch Contract (A11Y-02, D-08)

### Responsive popover width

Replace the flat `max-width: 320px` currently at `src/theme/tour.css:16` with:

```css
.driver-popover {
  max-width: min(320px, calc(100vw - 2rem));
}
```

This guarantees the popover never touches or overflows the viewport edge on narrow devices (~320-375px, the stated target range) while preserving the existing 320px cap on larger screens (unchanged visual behavior on desktop/tablet — this is a pure narrow-viewport fix, not a redesign). At exactly 320px viewport width, this resolves to `min(320px, 288px)` = `288px`, leaving a 16px margin per side — consistent with the app's own `p-4` (16px) content gutter (`page.tsx:371`) so the tour popover's edge inset visually matches the app's own edge inset.

### Placement — trust existing config, no blanket per-step overrides

driver.js's auto side-placement (no explicit `side` set on any step in `src/lib/tourSteps.ts:83-107`, meaning driver.js's own `side: 'auto'`-equivalent default governs) plus the existing `smoothScroll: true` (`page.tsx:199`) are kept as-is per D-08 — **do not add blanket per-step `side` values.** Only add an explicit `side` override for an individual step if mobile QA (device or emulated viewport testing during verification) demonstrates that step's popover visibly clips, overlaps its own anchor, or renders off-screen at 320-375px. Any such override must be recorded as a QA finding in the phase's verification artifact, not pre-guessed here — this contract deliberately does not enumerate per-step sides in advance.

### Touch hit-area

| Element | Minimum hit-area | Current state |
|---|---|---|
| Popover Next/Back/Done buttons | 44×44px (WCAG 2.5.5 AAA / iOS HIG minimum) | driver.js's default `.driver-popover-footer-btn` padding must be checked against this floor during implementation; if the rendered button (text + padding) falls under 44px tall at the 14px/`btn-sm`-equivalent sizing declared in Phase 1's contract, add `min-height: 44px` to `.driver-popover-footer-btn` in `tour.css` |
| "?" replay button | Already 52×30px content box (`h-[52px] w-[30px]`, `page.tsx:392`) matching the sibling share/theme-toggle icon buttons — the 52px height already clears the 44px floor; the 30px width is below 44px but matches the established sibling-button sizing convention (Phase 2 D-02 explicitly mirrors the share button's `h-[52px] w-[30px]`) | No change required — this is a pre-existing, deliberately-matched sizing convention from Phase 2, not a new gap to close. Flagging as reviewed, not a defect. |
| Popover close (×) button | Same 44px floor as Next/Back/Done | Same check/fix as above if driver.js's default padding falls short |

## RTL Contract (scoped to tour popover only)

`ar` and `ur` are 2 of the 30 supported locales (`src/lib/translations.ts:222`, `:302`). The app has no `dir="rtl"` handling anywhere today (confirmed: no `dir=` attribute in `src/app/layout.tsx`), and this phase does **not** add app-wide RTL support — only the tour popover's own rendering is addressed, per the phase's explicit scope boundary (deferred: "App-wide RTL layout support... beyond this phase").

| Aspect | Contract |
|---|---|
| Text direction | When the active `languageAtom` is `ar` or `ur`, the tour popover's title/body text must render RTL. Since driver.js's popover is a detached DOM node (not part of React's tree), this is set imperatively at `startTour()` time: after `driverObj.drive()` or via driver.js's `onPopoverRender` hook (available in 1.6.0), set `dir="rtl"` on the `.driver-popover` element itself (scoped — do NOT set `dir` on `<html>` or `<body>`, which would be app-wide RTL and is explicitly out of scope). |
| Button order | RTL convention places the "forward" action on the visual left and "back" on the visual right (mirrored from LTR). driver.js does not auto-mirror its footer button order. Contract: when `dir="rtl"` is applied to the popover, also add a scoped CSS rule (`[dir="rtl"] .driver-popover-footer { flex-direction: row-reverse; }` in `tour.css`) so Next/Done visually lands on the left and Back on the right, matching RTL reading-order expectations. Do not reorder the underlying DOM/tab order — screen reader/keyboard tab sequence stays logical (Back before Next in document order); only the visual flex order flips. |
| Arrow/placement mirroring | driver.js's popover arrow (`.driver-popover-arrow-side-{left,right,top,bottom}`, `tour.css:73-87`) is positioned based on which side of the anchor the popover renders — this is a physical (not logical) direction tied to actual viewport geometry, not text direction. **No mirroring needed**: the arrow already points at the correct anchor regardless of `dir`, because driver.js computes `side` from element bounding boxes, not from CSS writing-mode. Leave `tour.css:73-87` unchanged. |
| Progress text / counter | `"{n} / 8"` — numerals and the `/` separator are directionally neutral in both `ar` and `ur` (both use Western Arabic numerals in this UI convention, consistent with `translations.ts`'s existing pattern of un-transliterated numerals in other namespaces). No change needed. |
| Verification | Flagged as a QA risk in `03-CONTEXT.md` code_context — RTL popover rendering must be checked live (visual QA) for both `ar` and `ur` during phase verification, since driver.js's RTL behavior with a manually-set `dir` attribute is not documented/tested upstream. |
